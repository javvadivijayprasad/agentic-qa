## The verifier's six checks

1. work item was read — a **successful** `wit_work_item get` for **that** id;
2. a spec file exists — an artefact was recorded AND the file is on disk;
3. the suite ran and came back green — `green === true` on the **last** run;
4. at least `minCases` cases were created;
5. every created case carries `testsWorkItemId` = the story;
6. the cases were added to a suite.

Point 3 is the one that matters most. `pw.run_tests` sets `green: false` while anything is
skipped, and a generated skeleton is all `fixme`, therefore all skipped — so "the agent generated
tests and reported success" cannot pass. The gap message even distinguishes the two failures:
"6 test(s) are still unimplemented (fixme), so nothing was actually verified" versus
"4 passed, 2 failed".

Every gap carries an `evidence` object recording what the verifier DID see, so a reader can tell
"never tried" from "tried and was refused" from "tried and failed" — which is the distinction a
post-mortem actually needs.

## Context ordering

Three rules, in priority order: tool schemas are never trimmed (a model missing a schema invents
one); primary sources come first and are trimmed last (a model that has lost the acceptance
criteria starts making them up, while one that has lost its own earlier chatter merely repeats a
step); and gate feedback is never trimmed at any cap, because dropping a refusal makes the model
propose the refused call again until the step budget dies.

## Decisions taken (flag if you disagree)

- **The verifier reads the ledger, never the model's account of itself.** It takes no argument from
  the model and cannot be told that something happened.
- **Traceability is a done-condition, not a nicety.** A case not linked to the story fails
  verification even if the tests are perfect.
- **One retry on gaps** (unchanged from A2): gaps go back to the model once, and a second failure
  ends the run `blocked` rather than looping.
- **The skill lists tools, the gate lists permissions.** `allowedTools` only narrows what the model
  is shown, so it cannot spend steps proposing refusals. A test asserts every tool in the skill is
  classified by the manifest and none is always-refused, so the two files cannot drift apart.
- **The instructions tell the model it does not decide done.** They also name the exact `action`
  values, and a test checks those against the manifest.
