# Handoff — agentic-qa step A9: the file-approval contract (2026-09-14)

**For:** Vijay, and the platform agent · **From:** Claude session

This is the interface between the two tracks. Slice 1 is closed and pushed; what remains before
A10 is proving that the platform can drive a run without a terminal. Everything below is now
exercised by tests in `test/approvers.test.ts`, so it is a contract rather than an intention.

## The shape of it

```
aqa run "Write tests for AB#1" \
  --config ai-quality.config.yaml \
  --workspace examples/sandbox \
  --approval file \
  --approval-timeout 120 \
  --ledger .aqa
```

With `--approval file` nobody is at a keyboard. The run announces each approval in the ledger,
writes a request file, and waits. The platform answers by editing that file.

## The two files

**The ledger** — `.aqa/runs/<runId>/events.jsonl`, one JSON object per line, flushed as each event
is appended. Tail it. The event that matters here is:

```json
{ "kind": "approval_requested",
  "payload": { "approvalId": "apr-0001", "summary": "Approve 1 call: …", "calls": [ … ] } }
```

**The request** — `.aqa/runs/<runId>/approvals/apr-0001.json`, named by the `approvalId` the ledger
just announced. That naming is the whole of the coupling between the tracks.

```json
{
  "approvalId": "apr-0001",
  "summary": "Approve 4 calls: ado.testplan_test_case_write(…); …",
  "calls": [{ "toolName": "ado.testplan_test_case_write", "args": { "action": "create", … } }],
  "requestedAt": "2026-09-14T12:10:33.114Z",
  "decision": null
}
```

To answer, write the same object back with `decision` set to `"approved"` or `"denied"`, and
`by` set to whoever decided. `at` is optional; it is filled in if missing.

```json
{ …, "decision": "approved", "by": "vijay@…", "at": "2026-09-14T12:11:02.900Z" }
```

## Four things the platform must get right

**1. The ledger event lands BEFORE the file exists.** The loop appends `approval_requested` and
then calls the approver, which writes the file a moment later. So a platform that sees the event
and immediately stats the file will sometimes find nothing. Treat "not there yet" as _still
arriving_, not as an error. There is a test asserting this ordering, because it is the kind of race
that shows up once in fifty runs and is then blamed on something else.

**2. A partial write is ignored, not fatal.** The runtime polls the file and parses it; unparseable
content is skipped and polling continues. So writing the file non-atomically is survivable — but
write to a temp file and rename if you can, because it costs nothing.

**3. Silence is a no.** Past `--approval-timeout` (default 1800s) the answer becomes
`{ decision: "denied", by: "timeout" }` and the run ends `blocked`, exit 2. This is deliberate: an
unattended run must not sit forever holding a Playwright browser and an MCP server open. For a
smoke run, set it to 60–120 seconds so a mistake fails fast.

**4. One approval per cycle, many calls inside it.** The loop batches every gated call from one
cycle into a single request — that is why `calls` is an array. Render all of them. A reviewer
approving "create 4 test cases" as one decision is the point; four separate prompts is the thing
this design is avoiding.

## What comes back

| run status | exit | what the platform should show                                        |
| ---------- | ---- | -------------------------------------------------------------------- |
| `done`     | 0    | the verify event's `limitations`, if any, beside the result          |
| `error`    | 1    | the `end` event's summary                                            |
| `blocked`  | 2    | the verifier's gaps, or "approval denied", or the no-progress reason |
| `refused`  | 3    | scope refusal — happened before any token was spent                  |
| `budget`   | 4    | which budget, and the counts                                         |

Two things from A8 the run page needs, both already in the handoff for that step:

- **`VerifyPayload.limitations`** — checks that were not made, and why. A green run with limitations
  is not the same as a green run without them, and the difference should be visible rather than
  inferred. `aqa replay` puts them under "Checks not made".
- **`agent.capabilities`** — a third axis beside `policy` and `scope`. Not an operator decision; a
  fact about the account. Worth showing differently for that reason.

## The smoke itself

1. Platform starts `aqa run … --approval file --approval-timeout 120`, capturing the run id from
   the first stderr line.
2. Platform tails the ledger and renders events as they arrive.
3. On `approval_requested`, it polls for `approvals/<approvalId>.json`, shows the batch, and writes
   the decision when the reviewer answers.
4. Run reaches `end`; platform shows the status, the summary, the gaps or the limitations.

Worth doing **twice**, because the second run is the interesting one: with the story's tests already
written and its cases already linked, the agent creates nothing, asks for one approval (the summary
comment), and still ends `done`. A platform that assumes every run produces new artefacts will show
an empty or broken page for that case, and that case is the common one in real use.

## Changed in this step

- `--approval-timeout <seconds>` on `aqa run`. Contract addition, optional, default 1800.
- Four tests covering the joint path end to end: approve → `done` with `by` recorded, deny →
  `blocked` with no call made, silence → `blocked` by `timeout`, and the request file carrying the
  full batch while the ledger announces the id first.
