## The finding that shaped this step

`docs/tools-observed.md` showed that Microsoft's Azure DevOps MCP server does not expose one tool
per operation. It exposes one tool per subject area and selects the operation with an `action`
argument — and it mixes reads and writes inside the same tool:

| tool                           | some actions                                                            |
| ------------------------------ | ----------------------------------------------------------------------- |
| `ado.wit_backlog`              | `list`, `list_work_items`, **`reorder`**                                |
| `ado.wit_work_item_link_write` | `link`, **`unlink`**                                                    |
| `ado.pipelines_write`          | `run_pipeline`, `create_pipeline`, `rename_pipeline`                    |
| `ado.wit_work_item`            | `get`, `get_batch`, `list_comments`, `my`, `list_revisions`, `get_type` |

A class per TOOL is therefore wrong in both directions: classify `wit_work_item` as `read` and the
gate has no opinion about the tools that share its shape; classify `wit_backlog` as `write_record`
and reading a backlog needs a human approval. So governance moved down one level.

## Decisions taken (flag if you disagree)

- **A generated skeleton can never report a pass.** Every generated test is `test.fixme`, which
  Playwright reports as skipped, and `pw.run_tests` sets `green: false` whenever anything is
  skipped. The failure mode I most wanted to avoid is a pipeline that produces 40 vacuous tests and
  a green tick.
- **Test cases must be traceable.** `testplan_test_case_write.create` declares `testsWorkItemId` as
  its scope argument, so a case the agent cannot link back to an in-scope story is refused rather
  than created loose. This is stricter than Azure DevOps requires.
- **`wit_work_item_write` is NOT admitted.** Slice 1 creates test cases through the Test Plans tool,
  so the agent has no general "create/update any work item" capability. Nor does it have
  `wit_work_item_link_write`, `wiki_upsert_page`, `pipelines_write`, or any PR tool.
- **Playwright is observation-only for now.** `browser_snapshot`, `console_messages`,
  `network_request(s)`, `find` and `take_screenshot` are classified; `navigate`, `click`, `type`,
  `fill_form` and the rest are not, and `browser_evaluate` / `browser_run_code_unsafe` never will
  be. See the open question below — this is the one place where I would rather change the contract
  than fudge a class.
- **`TCG_URL` is the full endpoint**, not a base URL: the platform owns its routing and I will not
  invent a path. Tell the platform agent which URL to set.
- **`SYNTHDATA_CMD` is split on whitespace, no shell.** Quoted segments survive; pipes and
  substitutions do not work, by design.

## Open question for you (contract change, so I did not just do it)

Driving a browser needs a scope dimension we do not have: _which URLs may the agent touch?_
Without it, `browser_navigate` cannot distinguish a staging app from production, and classifying it
as `write_workspace` (execute, no approval) would be dishonest. The fix is to add `urls` to
`agent.scope` in `ai-quality.config.yaml` — a PLAN §0 change the platform agent has to mirror.

I would do it at slice 3 (failure → triage → heal), which is the first slice that actually needs a
browser. Say the word if you want it sooner and I will fold it into A6.
