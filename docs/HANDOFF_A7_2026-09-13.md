## Three decisions worth your attention

**Tool names are rewritten on the wire.** The Messages API only accepts
`^[a-zA-Z0-9_-]{1,128}$`, and every name we use is dotted — `ado.wit_work_item`. So the adapter
maps `.` to `__` going out and back coming in. The ledger never sees the wire name. Had I not
checked the constraint, every tool call would have failed at the API with a validation error.

**Each tool tells the model its own governance.** The description we send is the server's text plus
"Permitted action values: "get" (read), "get_batch" (read)… Any other action is refused" and
"Scope-checked argument(s): id — required". The model learns the boundary from the tool definition
rather than by spending a step being refused. This is cheap and it is the single biggest lever on
how many wasted cycles a run costs.

**No API-side conversation.** The obvious way to write this adapter is to keep a message history
with `tool_result` turns and let the API remember the run. I deliberately did not: every cycle is a
fresh, self-contained request assembled from the ledger by the context builder. The ledger is the
memory. That is what makes a run replayable months later, and what lets the paper claim the
transcript is complete — a conversation living inside the provider's message history would not be
either of those things.

Secondary but real: the model's stop note is now recorded in the ledger. A failed run shows the
model saying "all four cases created" on one line and the verifier saying `no-test-cases` on the
next. That contrast is the most informative thing in the artefact.

npm run typecheck && npm test && npm run lint && npm run build
npm run fixture:make && git status       # events.jsonl modified — expected, see below

Do **not** point it at the sandbox yet — that is A8, and it wants the work item's acceptance

reading your API key — the scope check runs first on purpose.
