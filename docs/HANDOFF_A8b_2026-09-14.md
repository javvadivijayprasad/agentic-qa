## The finding worth putting in the paper

**A test case is not a test plan.** Creating a test _case_ in Azure DevOps is an ordinary work-item
write and succeeds on a Basic licence — that is why work items 7–11 exist. Creating a test _plan_
or a test _suite_ goes through the Test Plans service, which requires the Test Plans access level, a
paid extension. Without it every attempt returns, verbatim:

    Error creating test plan: You are not authorized to access this API.
    Please contact your project administrator

Reads are unaffected: `testplan` with action `list_plans` succeeds and returns an empty list. So the
boundary is not "Test Plans works / does not work"; it runs straight through the middle of the
feature. Anyone reproducing this bundle on a free organisation will hit exactly this wall, and the
distinction is not documented anywhere obvious.

This is why `agent.capabilities` exists rather than a hard-coded assumption.

## Contract changes — the platform agent must mirror both

**1. `agent.capabilities`** (PLAN §0.3), a third axis beside `policy` and `scope`:

```yaml
agent:
  capabilities:
    test_plans: true # false on an account without the Test Plans access level
```

Optional, defaults to `{ test_plans: true }`, so existing configs still load — but it **changes the
config hash** recorded in the `request` event, so the fixture was regenerated and the platform track
must re-pull `examples/fixture-ledger/events.jsonl`. Still 42 events, no shape change.

The three axes answer different questions and should not be collapsed in the UI:

- `policy` — what the agent is _allowed_ to do. An operator decision.
- `scope` — _where_ it may act. An operator decision.
- `capabilities` — what the environment _can_ do. Not a decision at all; a fact about the account.

With `test_plans: false` the plan and suite tools are removed from the skill's view entirely (an
environment that cannot perform an operation should not advertise it), the instructions drop the
suite step and say why, and the verifier stops requiring suite membership.

**2. `VerifyPayload.limitations?: string[]`** — additive and optional. Checks the verifier did not
make, and why. A run can be done without being complete, and that difference belongs in the ledger
rather than in a footnote. `aqa replay` renders them under a **Checks not made** heading; the
platform run page should show them next to the gaps, visually distinct — a limitation is not a
failure, but a green run with limitations is not the same as a green run without them.

## Authorization failures are terminal

A call can fail because the arguments were wrong — retry, that is the right move — or because the
environment will not perform that operation for this identity at all. No argument list fixes the
second kind, and every retry costs a step, a model call, and a human's attention on an approval
prompt for a call already known to be dead.

Observed in run `20260914T015933Z-4a2806d0`: the plan creation was attempted four times. The model
varied `iteration` and `areaPath` between attempts, so the loop's repeat memo — which keys on the
exact arguments — never saw a repeat, and the reviewer was asked to approve the same doomed write
three more times. The run then spent its remaining cycles listing an empty plan list until the
no-progress rule ended it, 148 events in.

`denials.ts` fixes this in three parts:

- `authorizationFailure(result)` recognises the class from a deliberately **narrow** phrase list. A
  false positive silently removes a capability from a run, so "not authorized to access this API",
  "access denied", `TF400813`, `VS402455` and similar match, while "field not supplied", "does not
  exist", "socket hang up" and "500" do not. There are tests for both directions.
- `operationKey(tool, args)` identifies the **operation** — tool plus multiplexed `action` —
  so `ado.testplan_test_plan_write#create` closing does not close `ado.testplan#list_plans`, and
  shuffled arguments map to the same key instead of looking like a new call.
- The loop refuses a closed operation **before** the approval batch is assembled, and tells the
  model plainly that no retry and no variation can succeed.

On the observed run's shape this turns 4 calls and 3 approval prompts into 1 and 1.

## The other defects, briefly

Each was a run that failed, and each is now a test.

- **Elicitation.** The Azure DevOps server asks the client for `project` when it is missing; our
  client cannot answer, and the run died with "Client does not support form elicitation".
  `ServerSpec.defaultArgs` fills it in **before** gating, so the ledger and the policy event record
  the arguments actually sent.
- **No-progress stop** (`MAX_STALE_CYCLES = 3`). Observed: the same two files read 29 times.
- **...and its reverse.** The first version of that rule blocked the legitimate `pw.run_tests`
  re-run after a spec edit, and the model rewrote the spec **13 times** working around it. A
  successful call that produced artefacts, or that is not a read, now clears the memo.
- **Notes feedback.** Each cycle is assembled from the ledger rather than from an API-side
  conversation — that is what makes a run replayable — but without its own notes the model receives
  identical input and makes an identical decision. `NOTE_WINDOW = 4`.
- **Context windows by role.** `SOURCE_CHARS = 16_000` for primary sources, `STEP_CHARS = 2_000`
  for step results. A flat 400-character cap had been truncating the acceptance criteria the agent
  had just read, so it read the work item again, and again.
- **Windows spawn.** Node refuses to spawn a `.cmd` directly (`EINVAL`); `spawnable()` runs it
  through `ComSpec`.
- **ADO auth.** `--authentication envvar` with the PAT in `ADO_MCP_AUTH_TOKEN`, passed through the
  child process environment and never argv. The server's default is interactive browser OAuth,
  which opened a browser window mid-run.
- **Credentials.** The skill names `AQA_APP_USER` and `AQA_APP_PASS` exactly and forbids falling
  back to credentials the model happens to know — observed: it invented `AQA_USER_EMAIL`, then
  signed in as the Juice Shop administrator, which tests the wrong account and would have left a
  password in the repository.
- **Budgets** raised to 60 steps / 1,500,000 tokens. A fix → run → fix cycle costs roughly 14k
  tokens, most of it the fixed tool schemas.

## What you do

```
npm run typecheck && npm test && npm run lint && npm run build
npm run fixture:make && git status     # events.jsonl already regenerated; should stay clean
git add . && git commit -m "feat: terminal authorization failures, agent.capabilities (A8b)" && git push
```

Then, before the next run:

1. **Access level** — Organization settings → Users → your row → Access Level. If it reads
   **Basic**, set `capabilities: { test_plans: false }` in `examples/ai-quality.config.yaml`. If it
   reads **Basic + Test Plans**, the cause is a project permission on the area path instead.
2. Juice Shop up: `docker run --rm -d -p 3100:3000 --name juice-shop bkimminich/juice-shop`
3. `node dist/cli.js run "Write tests for AB#1" --config examples/ai-quality.config.yaml --workspace examples/sandbox`
